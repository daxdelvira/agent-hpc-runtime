\section{System Overview}

\sysname is a runtime that manages a single host-memory budget shared by two
kinds of resource: language models backing an agent's reasoning and
tool-calling steps, and the scientific data artifacts those tools consume.
It has two components.

The \textbf{retention arbitrator} decides which resources remain resident
between uses, and at which level. It is the primary component and it acts at
every point where memory pressure forces a choice. The
\textbf{opportunistic prefetcher} moves resources toward residency ahead of
need, and is deliberately subordinate: it consumes memory that retention did
not claim, and may displace a resident resource only under a conjunction of
strict conditions.

Both components score candidates with one value function, so a decision to
stage something and a decision to keep something are directly comparable
rather than governed by separate policies competing for the same memory.

\subsection{Residency states}

\sysname can hold a resource in one of three states, and the arbitrator's job
is to choose one per resource (Table~\ref{tab:states}).

\begin{table}[t]
\centering\small
\begin{tabular}{@{}lll@{}}
\toprule
State & Model & Data artifact \\
\midrule
Active   & serving on device      & activated in a live worker \\
Held     & weights in host memory & activated structure retained \\
Released & process terminated     & worker terminated \\
\bottomrule
\end{tabular}
\caption{Residency states. \emph{Held} is the state the arbitrator budgets:
it costs host memory and makes the next use cheap.}
\label{tab:states}
\end{table}

For a model, the held state parks weights in host memory while keeping the
serving process, its device context and its allocator alive; returning to
active is a wake rather than a boot, and in our deployment reduces a
$782$\,s cold start to $2.1$\,s. For a data artifact, the held state is a
resident worker process that keeps the parsed, in-memory structure across
tool invocations, so a subsequent use skips construction entirely.

The two held states are the same kind of object as far as the operating
system is concerned: anonymous memory belonging to a live process, invisible
to any file-backed cache and chargeable to one allocation. That is why a
single arbitrator manages both, and why the choice between them is a real
one --- a parked model and a retained database compete for exactly the same
bytes.

\section{The Retention Arbitrator}

At each decision point the arbitrator selects the set of resources to leave
in the held state. Let $g(r)$ be the memory $r$ occupies while held, $B$ the
budget, and $\Delta t(r)$ the estimated time until $r$ is next required.
Writing $\mathrm{cold}(r)$ for the cost of producing $r$ from scratch and
$\mathrm{ready}(r)$ for the cost of resuming it from the held state, the
saving retention buys is $\mathrm{cold}(r) - \mathrm{ready}(r)$.

Ranking on that saving alone is not enough, because it is indifferent to
when the resource is next needed: a resource required in ten seconds and one
required in three hours would compete equally for the same memory, and the
budget fills with resources that will not be used soon. Ranking on saving per
unit of time-to-use is not enough either, since it collapses the difference
between a large saving and a small one whenever both are imminent.

\sysname resolves this with an explicit \textbf{planning horizon} $H$:

\begin{equation}
v(r) \;=\; \bigl(\mathrm{cold}(r) - \mathrm{ready}(r)\bigr)
           \cdot \frac{H}{\max\!\left(\Delta t(r),\, H\right)}
\label{eq:value}
\end{equation}

\noindent and ranks by \emph{value density} $v(r)/g(r)$ --- seconds of stall
avoided per gigabyte held.

$H$ is what makes the two regimes behave differently, and the system cannot
do without it. Inside the horizon, resources are compared on absolute
seconds saved: everything in that window is going to be needed soon, so the
question is simply which resource saves the most, and a small imminent
candidate does not get to outrank a large one merely by being sooner.
Outside the horizon, value decays as $H/\Delta t$, so a resource that will
not be touched for a long time surrenders its memory to one that will. A
system without $H$ has to pick one of these behaviours globally and gets the
other regime wrong.

$H$ also gives the prefetcher and the arbitrator a shared notion of ``soon,''
which is what allows staging and retention to be scored in one currency
(\S\ref{sec:prefetch}). It is a tunable, and the natural setting is on the
order of the workflow's typical inter-step gap.

\subsection{Selection under indivisibility}

Held resources cannot be partially surrendered. Half a model's weights serve
no requests, and a partially retained structure does not answer queries, so
release is all-or-nothing. Selection is therefore a subset choice under a
capacity constraint rather than a sequence of independent evictions, and
\sysname evaluates it as one: it searches for the highest-value set that
fits, rather than repeatedly discarding the worst-ranked resident. The
distinction matters whenever admitting one large resource requires releasing
two smaller ones --- a decision single-victim eviction cannot express.
Algorithm~\ref{alg:arb} states the resulting decision procedure.

Ties are broken toward the smaller total footprint, so equal value never
costs extra budget.

\subsection{Horizon estimation}
\label{sec:horizon}

The arbitrator's only external input is $\Delta t(r)$, and \sysname obtains
it from two sources at different granularities.

\textbf{Coarse.} Agentic workflows are organised by a planner that commits to
a sequence of steps before executing them. That plan is a long-range but
incomplete signal: it names the tools the workflow intends to run and their
order, which reaches far ahead, but agents routinely execute steps the plan
does not enumerate and depart from it under tool failures or intermediate
results.

\textbf{Fine.} A transition model built from observed executions supplies the
local complement: a distribution over the immediate successors of the current
step. This is short-range but covers exactly the region where the plan is
silent or has been departed from.

The two are merged into a single predicted step sequence --- the plan
supplying structure, the transition model filling and correcting it near the
present --- and each step carries an expected duration. A position in that
sequence therefore converts to a time, and $\Delta t(r)$ is the summed
expected duration of the steps between now and the earliest predicted step
that requires $r$. Because the two sources may disagree, each estimate
carries a confidence derived from their agreement and from the sharpness of
the successor distribution; the arbitrator applies it as a weight, so an
uncertain horizon perturbs a ranking rather than forcing a decision.

One property of this estimator is load-bearing for the arbitrator. Lookahead
is bounded, so the predictor reports \emph{not required within $H$} rather
than \emph{not required again}. The arbitrator treats the two very
differently: the first is a low rank that still competes for spare memory,
while the second would be licence to discard. Preserving that distinction
keeps a resource eligible whenever the budget has room for it, independently
of how far ahead the estimate can see.

\begin{algorithm}[t]
\small
\caption{Residency decision}
\label{alg:arb}
\begin{algorithmic}[1]
\State \textbf{input:} candidates $\mathcal{R}$, budget $B$, horizons $\Delta t(\cdot)$
\For{$r \in \mathcal{R}$ currently held or active}
  \State $w_r \gets v(r)$ \Comment{Eq.~\ref{eq:value}, retention}
\EndFor
\For{$r \in$ \textsc{StageCandidates}}
  \State $w_r \gets v_{\text{stage}}(r)$ \Comment{same currency}
\EndFor
\State $S \gets \arg\max \sum_{r \in S} w_r \;\; \text{s.t.} \sum_{r \in S} g(r) \le B$
\State release $\mathrm{held} \setminus S$; hold $S \setminus \mathrm{held}$
\end{algorithmic}
\end{algorithm}

\subsection{Device capacity}

A model actively serving on an accelerator holds its weights in device
memory and does not charge the host budget. The arbitrator therefore treats
device residency as a separate, smaller capacity, and considers for host
retention only what has been displaced from it. The two capacities are
managed together: releasing a model from the device is what creates a
candidate for the held state, and the arbitrator decides in the same step
whether that candidate is worth its host memory or should be released
outright.

\section{The Opportunistic Prefetcher}
\label{sec:prefetch}

The arbitrator acts on resources the workflow has already used. The
prefetcher acts on resources it has not: drawing on the same horizon
estimates (\S\ref{sec:horizon}), it moves a resource toward residency before
the need arrives, so that construction or transfer overlaps computation
rather than blocking it.

Staging is scored in the same currency as retention, with one difference in
how the saving is computed. Retention saves the full
$\mathrm{cold}(r) - \mathrm{ready}(r)$ whenever the resource is next used,
because the work is already done. Staging saves only as much of that cost as
fits in the interval before the need --- a stage that gets halfway leaves the
remainder exposed. Its benefit is therefore capped by $\Delta t(r)$, and
Eq.~\ref{eq:value} applies to that capped quantity. Sharing $H$ across both
is what puts them on one scale: within the horizon they are compared as
seconds saved, so a small imminent stage cannot outrank a large retention
simply for being nearer.

\subsection{Slack first}

The prefetcher's default is to consume only \textbf{slack}: memory the
arbitrator has left unclaimed. If the resource does not fit in unused
budget, the stage is abandoned rather than funded by displacing something
resident.

This is the operating mode for the large majority of staging decisions, and
it is what makes speculation safe here. A stage that consumes only slack has
its downside bounded by wasted bandwidth --- it cannot cost a retention that
would have been worth more --- so its expected value stays positive across a
wide range of horizon quality rather than requiring precision to break even.
Where a conventional prefetcher's value scales with accuracy, slack staging's
does not, because the memory it uses had no competing claim.

\subsection{The outbid path}

Restricting staging to slack forgoes cases where a stage genuinely is worth
more than an incumbent. \sysname permits displacement, but only when every
one of the following holds:

\begin{enumerate}\itemsep2pt
\item \textbf{Margin, not tie.} The stage's value density must exceed the
      incumbent's by a configured margin, so that estimation noise alone
      cannot reorder them.
\item \textbf{Completable.} The predicted window must be long enough to
      finish the stage before the need. A stage that cannot complete converts
      a certain retention into a partial, speculative saving.
\item \textbf{Incumbent not imminent.} The displaced resource's own horizon
      must lie beyond $H$ --- outside the window in which the system compares
      candidates on absolute savings.
\item \textbf{Confidence.} The horizon estimate must carry confidence above a
      threshold, since displacement is the one staging action whose cost is
      not bounded by slack.
\end{enumerate}

\noindent The conditions are conjunctive and deliberately conservative. Their
combined effect is that the prefetcher behaves as a slack consumer under
normal conditions and acquires the ability to displace only when the evidence
is strong and the incumbent is demonstrably idle --- so the arbitrator, not
speculation, remains in control of the budget.
